## Места для кеширования
Стоит закешировать API MES при чтении заказов в статусе "MANUFACTURING_APPROVED". Кеш будет обновляться при чтении из MQ события об изменении статуса заказа на "MANUFACTURING_APPROVED" и при изменении статуса заказа на "MANUFACTURING_STARTED" через MES API

## Мотивация
Сейчас есть проблема медленной подгрузки дашборда для операторов, стоит закешировать данные для этого дашборда - тогда мы уменьшим задержку перед началом работ над изделием и ускорим выполнение заказов для клиентов. 

## Предлагаемое решение
  Выбрана стратегия Write-Through - сперва обновляем БД, затем обновляем кеш в синхроне. Но нужно учесть: есть риск что оператор увидит в списке заказ, который уже взяли в работу(если при обновлении кеша произошла ошибка) - нужна защита от двойной работы над одним заказом (например, через проверку статуса в БД момент обновления UPDATE order SET status='MANUFACTURING_STARTED', operator='оператор' WHERE id='номер заказа' and status='MANUFACTURING_APPROVED')
  Почему не выбраны:
  - Refresh-Ahead - более сложен в реализации в сравнении с Write-Through, значительного выигрыша не дает в кейсе выбора оператором заказа для работы.

### Стратегия инвалидации кеша
Выбрана стратегия "по ключу" - если заказ уходит со статуса MANUFACTURING_APPROVED - инвалидируем кеш точечно для заказа.
Стратегия "временная" не дает такую актуальность кеша как выбранная.
