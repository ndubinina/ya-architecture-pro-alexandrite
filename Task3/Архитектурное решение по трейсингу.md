## Места для трассировки
Системы, которые стоит покрыть трейсами:
- Shop API, CRM API, MES API - при получении запросов от внешних компонентов, при обращении во внешние компоненты (БД, s3, RabbitMQ)

Где заказ может зависнуть:
- между CRM API и MES API (для B2C), между MES API и CRM API (для B2B) - сообщения могут потеряться при передаче через RabbitMQ, особенно если очереди не персистентные или нет DLQ
- между Shop API и MES API (при расчете стоимости, долгий асинхронный процесс) 
- в момент назначения оператору - дашборд MES грузиться долго, что замедляет прием заказа в работу

Список данных для каждого спана:
- trace_id, span_id - идентификаторы трассировки (должны повторяться в логах)
- order_id, client_id - идентификаторы клиенты и заказа
- is_sync - признак синхронного или асинхронного взаимодействия
- request_at, response_at - получение компонентом запроса и время ответа
- duration - длительность
- result - результат (код ответа/статус выполнения)
- error - информация об ошибке (при наличие)
- source_system - система-источник
- destination_system - целевая система
- endpoint/queue_name - тип операции 

## Мотивация
Добавление трейсов позволит:
- быстро локализовывать причины неработоспособности системы в случае инцидентов, что уменьшит время простоя системы и меньшее число заказов пострадает
- выявлять узкие места в процессе обработки заказов

## Предлагаемое решение
Нужно развернуть сервер Jaeger для хранения и визуализайции трейсов

Нужно внедрить Open telemetry SDK в 
- Shop API (Spring Boot)
- CRM API (Spring Boot)
- MES API (C#)

[Схема предполагаемого решения](./../jewerly_c4_model.drawio)

### Безопасность
- Необходимо запретить прямой доступ к хранилищу Jaeger (доступ ограничен только администраторам в соответствии с ролями)
- Доступ к UI Jaeger организовать по группам (разработчик, dev ops)
- Чувствительную информацию в трейсы не отправлять: персональные данные клиента, токены, стоимость заказа, платежные данные

## Компромиссы
- трассировать на уровне БД не будем, достаточно большое число запросов, можно будет добавить трассировку в случае выявления медленных запросов
- пишем минимально необходимый объем данных в трейсы, для подробного анализа - нужно будет смотреть логи (для этого необъодимо логировать trace_id)
